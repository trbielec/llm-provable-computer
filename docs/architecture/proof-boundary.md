# Proof Boundary

## Current Trust Model

The repository contains multiple execution backends for the same compiled program:

- `TransformerVm`
- `NativeInterpreter`
- `BurnRuntime`
- `OnnxRuntime`

These do not all sit inside the current STARK proof boundary in the same way.

## What the STARK Currently Proves

The vanilla STARK path proves:

- the execution trace generated by the native ISA interpreter

This is implemented in `src/proof.rs`, where `prove_execution_stark()` reconstructs a `NativeInterpreter`, runs it, and proves the resulting trace.

## What Is Cross-Checked Instead

The transformer-shaped runtime is not yet directly proved by the STARK.

Instead, it is checked against the same semantics through lockstep verification:

- transformer vs native
- optionally Burn vs native
- optionally ONNX vs native

This is implemented in `src/verification.rs`.

## Practical Meaning

Today the system gives you:

1. a deterministic compiled transformer runtime,
2. a semantic oracle for the ISA,
3. a proof of supported ISA execution,
4. cross-engine checks that the transformer runtime matches that ISA semantics.

So the precise claim is:

- "the supported VM execution is proved, and the transformer backend can be checked against it"

not:

- "the transformer forward pass itself is currently what the STARK proves"

## Why This Still Matters

This is still useful because it separates concerns cleanly:

- semantics are small and auditable
- the proof targets a stable execution model
- alternative runtimes can be checked against the same semantics

That makes the current architecture a good base for:

- proof-carrying rule execution
- backend portability checks
- future work toward direct transformer-trace proving
